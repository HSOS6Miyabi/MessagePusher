# 安全与数据处理注意事项

本文说明 MessagePusher 已实现的安全措施，以及部署人员需要负责的运行保护。请按 [操作手册](operations.md) 完成备份和故障处理。

## 1. 各类凭据的用途

| 凭据或配置 | 用途 | 保存要求 |
| --- | --- | --- |
| `CONFIG_KEY_BASE64` | AES-256-GCM 加密/解密个人 Provider 设置；解码后应为 32 字节 | 与数据库备份配套保存在受保护位置 |
| `JWT_SECRET` | 签发和验证管理页面的登录令牌；至少 32 字符 | 独立随机生成，限制读取权限 |
| `POSTGRES_PASSWORD`、`DATABASE_URL` | PostgreSQL 连接认证 | 不放入代码、截图、日志或提交记录 |
| `ADMIN_PASSWORD` | 数据库用户表为空时创建首个管理员 | 首次部署后改用页面修改账户密码 |
| `RELAY_SECRET` / `RELAY_SECRETS` | 代理验证带时间戳的 HMAC-SHA256 请求 | 主程序的个人渠道和代理分别安全配置 |
| 个人 Provider 凭据 | Telegram、企业微信、SMTP、Resend 的平台身份信息 | 由渠道所有者录入，使用时按需解密 |
| API 发送密钥 | 允许向指定用户账户的已启用渠道提交消息 | 创建后只显示一次；数据库保存 SHA-256 摘要 |

登录密码使用 Argon2 处理。登录令牌有效期为 24 小时。修改密码和账户管理操作会按照会话版本及账户启用状态检查令牌。撤销 API 密钥后，该密钥不能继续提交消息。

## 2. 用户权限与数据访问

管理员可以管理用户、注册开关、站点公开信息和 Provider 类型的开放状态；普通用户管理自己的渠道、发送密钥与消息。`src/api.rs` 按用户 ID 限制用户对渠道、密钥和历史记录的访问。

渠道详情接口只返回可以展示的非敏感字段及凭据是否已保存，平台密码和 Token 不会作为详情内容返回。拥有数据库访问权限及 `CONFIG_KEY_BASE64` 的维护人员能够处理加密后的记录，因此这两项权限需要分别保护。

## 3. 数据存储与传输

- `events` 保存消息标题、正文和 Base64 形式的附件。当前程序不会自动删除历史消息。
- 渠道的 `encrypted_settings` 使用 AES-256-GCM 加密存入数据库。`events` 的正文与附件没有在应用层单独进行相同加密；请根据需求保护 PostgreSQL 数据卷和备份。
- 每条消息最多包含五个附件，原始附件总大小不超过 2 MiB；主要请求有 HTTP 请求体大小限制。
- 邮件、Telegram 和企业微信是第三方接收方。发送时会将必要的内容及相关平台凭据交给对应平台；使用代理时，代理也会接收消息内容与所需凭据，因此应仅使用可信代理。
- 公网入口使用 HTTPS，并尽可能限制数据库的网络可见范围。`PUBLIC_BASE_URL` 必须与订阅授权的公开地址一致。

## 4. 消息代理与网络访问

Rust 侧的代理配置默认只接受 HTTPS URL，`ALLOW_HTTP_RELAY=1` 仅供隔离测试环境使用。代理使用时间戳及 HMAC-SHA256 验证请求，允许的时间偏差由代理实现控制，代理调用第三方平台的目的地址在代码中固定。

个人渠道可以填写代理 URL，主程序目前没有内置目标主机地址白名单。开放公开注册或其他不可信用户使用权限时，应在主程序运行环境中设置出站网络限制，尤其要保护内部地址和云服务元数据接口。是否增加应用层地址限制，应作为后续安全改进事项评估。

`RELAY_SECRETS` 可在密钥更新期间包含多个逗号分隔的共享密钥。应先让代理接受新旧值，再更新个人渠道，最后停止接受旧密钥。

## 5. 订阅及接收者绑定

Telegram 的订阅链接有效期为 15 分钟，订阅代码仅以摘要形式存储，Webhook 回调需提供对应的请求密钥。企业微信成员授权使用相应的 OAuth 回调流程。请限制这些回调路径的实际用途，正确配置 HTTPS 和平台端的回调地址。

测试 Telegram 机器人时应使用专门的测试账户，避免修改生产机器人的 Webhook 或向真实用户发送测试消息。

## 6. 密钥更换与事件处理

1. 确认受影响的密钥种类及关联用户、渠道和代理。
2. 临时限制受影响的访问范围；使用管理页面撤销受影响的发送密钥。
3. 在对应第三方平台更换 Token 或授权码，并更新个人渠道保存的配置。
4. 更换代理共享密钥时按上一节的顺序逐步修改。
5. 更换 `JWT_SECRET` 会使既有登录令牌无法通过验证，使用者需要重新登录。
6. `CONFIG_KEY_BASE64` 对所有已有加密 Provider 设置至关重要。更换时需要准备并验证重新加密方案和数据库备份，不应直接替换为新值。
7. 检查数据库任务状态、日志及实际接收者的通知结果，记录事件和处理日期。

请不要把完整 JWT、API 密钥、邮件密码、机器人 Token、数据库连接字符串、生产备份或用户消息内容放进公开 Issue、GitHub Actions Artifact 或文档示例。

## 7. 安全检查入口

- 账户和渠道权限：`src/api.rs`、`src/site.rs`、`src/catalog.rs`
- 密码和加密：`src/security.rs`
- 代理签名：`src/security.rs`、`relay/core.js`
- Provider 输入验证：`src/models.rs`
- Webhook 与订阅授权：`src/subscribe.rs`
