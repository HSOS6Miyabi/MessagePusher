# 性能设置与负载测试

本说明介绍 MessagePusher 的并发发送、数据库访问及消息代理合并发送方式，并提供可重复运行的本地负载测试。测试数据使用模拟 Provider，不会向真实用户发送通知。

## 1. 关键运行参数

主程序提供以下环境变量：

| 环境变量 | 默认值 | 允许范围 | 用途 |
| --- | --- | --- | --- |
| `WORKER_CONCURRENCY` | `32` | 1–128 | 单个主程序实例同时处理的发送任务数量 |
| `DATABASE_MAX_CONNECTIONS` | `24` | 4–128 | 单个主程序实例使用的 PostgreSQL 连接池最大连接数 |

在 `.env` 中设置：

```dotenv
WORKER_CONCURRENCY=32
DATABASE_MAX_CONNECTIONS=24
```

使用 Docker Compose 时，修改环境变量后执行：

```bash
docker compose up -d
```

运行普通服务器二进制文件时，在启动进程之前设置相同的环境变量。程序在启动时验证范围，不接受范围外的数值。

并发数是单个主程序实例的限制。如果同时运行三个主程序实例，且每个实例允许 32 个发送任务，理论上最多会有 96 个并行发送任务。实际速度受平台调用频率限制、网络延迟、任务大小及机器资源影响。

## 2. 消息从 HTTP 请求到发送完成

调用 `POST /v1/send` 时：

1. 验证发送密钥、消息格式及用户有权使用的渠道。
2. 在 PostgreSQL 事务中写入一条事件记录。
3. 通过一次批量插入，为所有目标渠道建立发送任务。
4. 在同一事务中发送 PostgreSQL 通知，并提交事务。
5. 向调用方返回 HTTP 202 和消息 ID。
6. 后台工作进程收到通知后领取任务，异步向 Provider 发送消息。

工作进程每次最多领取 16 个任务，同时处理的任务总数由 `WORKER_CONCURRENCY` 控制。一个任务完成后，工作进程可以立即领取下一个任务，无需等其他任务完成。

后台从 PostgreSQL 领取任务时使用 `FOR UPDATE SKIP LOCKED`，多个主程序实例可以安全地并行领取尚未被其他进程领取的任务。

## 3. 代理合并发送

若多个渠道使用同一个代理 URL 和共享密钥，后台会把这些渠道的任务组合为一个代理请求，代理再并行发送各个平台。

主程序限制每个代理请求的编码后大小不超过 3.4 MB。如果任务组合后超过限制，主程序会分成多个请求。每个任务仍然保存单独的发送结果。

代理返回一组发送结果后，主程序通过一次数据库更新保存同一批次的任务状态。即使某个平台拒绝消息，其他平台的结果仍然会记录。

## 4. 运行本地负载测试

仓库中的 `scripts/benchmark.mjs` 使用 Node.js 自带的 HTTP 服务创建一个模拟消息代理，验证主程序的消息写入、后台任务领取、合并发送、代理签名和结果保存过程。

**建议使用单独的 PostgreSQL 数据库和测试服务器。** 测试会创建临时账户、渠道、发送密钥和一定数量的消息。在正常结束时会删除临时账户及相关数据。

### 4.1 准备主程序

测试所用模拟代理通过本机 HTTP 地址访问，因此测试环境需要额外设置：

```dotenv
ALLOW_HTTP_RELAY=1
```

这个设置仅供本机测试使用。正式部署的消息代理应使用 HTTPS，不要在公开生产环境中开启 HTTP 代理支持。

还需要设置测试用的管理员账号，并启动主程序及 PostgreSQL。

### 4.2 执行测试

将以下值替换为测试环境中的实际用户名与密码：

```bash
export MP_BENCH_URL='http://127.0.0.1:8080'
export MP_BENCH_ADMIN_USERNAME='administrator'
export MP_BENCH_ADMIN_PASSWORD='TEST_ADMIN_PASSWORD'

node scripts/benchmark.mjs \
  --messages=400 \
  --concurrency=48 \
  --providers=4 \
  --relay-delay-ms=40
```

参数说明：

| 参数 | 说明 |
| --- | --- |
| `--messages` | 要提交的消息数，允许 1–5000 |
| `--concurrency` | 客户端同时发送的 HTTP 请求数，允许 1–200 |
| `--providers` | 每条消息使用的模拟推送渠道数，允许 1–12 |
| `--relay-delay-ms` | 模拟代理每次 HTTP 请求等待的毫秒数，允许 0–3000 |

例如使用 400 条消息、每条消息四个渠道时，数据库会创建 400 条事件记录、1600 个发送任务。

模拟代理使用正确的 HMAC-SHA256 签名验证，并统计接收的请求数量、包含的任务数量及同时运行的请求峰值。它会立即按配置时间模拟处理完成，不会访问 Telegram、SMTP 或其他外部平台。

### 4.3 查看测试结果

测试完成时输出 JSON，主要字段如下：

| 字段 | 含义 |
| --- | --- |
| `enqueue_messages_per_second` | HTTP 客户端每秒成功提交的消息数 |
| `enqueue_latency_ms_p50` | 50% 的消息提交请求在此时间内返回 |
| `enqueue_latency_ms_p95` | 95% 的消息提交请求在此时间内返回 |
| `verified_deliveries_per_second` | 从开始提交到全部发送结果核实完成，平均每秒完成的任务数 |
| `relay_http_requests` | 实际调用模拟代理的 HTTP 请求次数 |
| `average_deliveries_per_relay_request` | 平均每个代理请求包含多少个任务 |
| `concurrent_relay_requests_peak` | 同时等待模拟代理响应的最大请求数 |
| `successful_deliveries` | 已在 PostgreSQL 中确认发送成功的任务数 |

`enqueue_latency_ms_p95` 越低，表示大部分发送 API 请求越快返回；`average_deliveries_per_relay_request` 越高，通常表示代理能够减少请求次数。

这里的完成时间包含调用消息状态查询接口所需的时间，因而也会受到数据库读取速度的影响。

### 4.4 比较不同配置

在同一台机器、同一个数据库配置和相同的模拟延迟下，分别测试：

- `WORKER_CONCURRENCY=8`、`32`、`64`。
- `DATABASE_MAX_CONNECTIONS=12`、`24`、`48`。
- 每条消息使用 1、4 或 8 个模拟渠道。
- 模拟代理延迟 20、100 或 300 毫秒。

每种配置至少重复执行三次，再比较提交延迟和发送完成速度。测试之间应确保数据库没有尚未处理的测试任务。

如果调高并发数后速度没有继续提升，应检查 CPU 使用率、内存、PostgreSQL 活跃连接数、磁盘写入速度和外部 Provider 的响应时间。

## 5. 注意数据库连接数

`DATABASE_MAX_CONNECTIONS` 是每个主程序实例的连接池上限。使用多个实例时，所有实例连接数之和应小于 PostgreSQL 配置的 `max_connections`，同时为管理工具和其他应用保留连接。

外部 HTTP 请求处理过程中不会一直占用数据库连接。工作进程读取任务后释放连接，待外部平台返回时才再次写入发送结果。

## 6. 附件和内存占用

每条消息最多可包含五个附件，原始总大小不超过 2 MiB。文件内容以 Base64 格式保存在数据库中。

当并发发送包含较大附件的消息时，工作进程需要同时读取多个任务的附件数据，内存使用量会明显增加。建议在经常发送大文件的场景下将 `WORKER_CONCURRENCY` 设置得较低，并监测实际内存消耗。

最近消息列表只统计最近 50 条事件，避免随历史记录增加而统计全部事件。查看消息详情时，页面只接收附件名称和类型，不会接收文件内容。

## 7. 失败重试与运行可靠性

工作进程收到新消息通知后立即读取任务。失败的任务会按照 PostgreSQL 记录的下次尝试时间唤醒，最多尝试五次。

每次领取任务都会记录领取次数。工作进程写入最终发送结果时会核对这些信息，避免已过期的发送任务覆盖新工作进程保存的结果。

PostgreSQL 通知连接中断期间可能遗漏通知，因此主程序还会进行最长间隔 60 秒的恢复检查。这个低频检查用于恢复异常情况。

## 8. 如何解释测试结果

模拟代理测试能够检查主程序、数据库、队列调度和批量 HTTP 请求的整体表现。它不包含实际 Telegram、企业微信和 SMTP 提供商的网络延迟、调用频率限制及附件处理时间。

因此，请分别记录两类测试：

1. **本地模拟测试**：测量主程序和数据库能够处理多少条消息。
2. **真实 Provider 测试**：验证目标平台实际接收消息的时间、成功率和频率限制。

不要将模拟代理的吞吐量直接当作真实 Telegram 消息的可持续发送速度。
