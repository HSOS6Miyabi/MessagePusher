# 设计决定

这里记录当前实现中会影响维护、扩展和部署的技术选择。修改重要方案时，在本文件增加新的决定或更新对应决定，并核实有关测试和文档。代码始终以仓库当前分支为准。

## D-01 使用 PostgreSQL 保存任务

**方案：** 在 `events` 保存消息内容，每个目标渠道在 `deliveries` 中保存独立发送状态。

**理由：** 用户数据、渠道配置和发送任务可以在同一数据库事务中保存；进程重启后仍可查找未完成的任务。

**影响：** 数据库磁盘、索引与连接数量会影响吞吐量。附件保存在 `events.attachments`，需要制定数据保留和备份策略。

**实现：** `migrations/`、`src/api.rs`、`src/delivery.rs`。

## D-02 通过 PostgreSQL 通知唤醒工作进程

**方案：** 新任务在数据库事务内执行 `NOTIFY messagepusher_delivery`；工作进程使用 `PgListener` 等待通知，按下一次重试时间唤醒，并使用最长 60 秒的恢复检查。

**理由：** 减少空闲时查询数据库的次数，同时能够在丢失即时通知后恢复任务处理。

**影响：** 通知只用于唤醒，任务与发送结果以数据库记录为准。多实例使用 `FOR UPDATE SKIP LOCKED` 避免同时领取同一任务。

**实现：** `src/delivery.rs`、`src/api.rs`、`src/catalog.rs`。

## D-03 为发送任务设置租约与重试

**方案：** 领取任务后设置 75 秒租约，最多尝试五次；失败后按照递增的等待时间重试，记录最后一次错误。单个进程默认允许 32 个并发任务。

**理由：** 网络调用可能失败或超时，需要在进程退出后继续发送，并限制同时消耗的资源。

**影响：** 外部平台已接受请求而本地状态尚未保存时，可能再次发送。业务调用可以使用 `Idempotency-Key` 减少重复创建。

**实现：** `src/delivery.rs`、`src/models.rs`、[队列说明](queue.md)。

## D-04 使用可选的无状态消息代理

**方案：** Rust 主程序可以直接发送；Telegram、企业微信和 Resend 还可通过 Vercel 或 Cloudflare Workers 上的代理发送。代理请求使用 HMAC-SHA256、时间戳和共享密钥验证。SMTP 只由主程序处理。

**理由：** 让网络受限的主程序通过可访问第三方平台的服务完成发送，同时使用户和任务记录留在 PostgreSQL。

**影响：** 代理会在请求处理期间接触到发送内容与平台凭据，应选用可信的代理部署环境并控制网络访问。

**实现：** `src/delivery.rs`、`relay/core.js`、[安全事项](security.md)。

## D-05 区分 Provider 类型开放状态与个人配置

**方案：** 管理员修改 `provider_catalog` 中的类型开放状态；每个用户独立维护自己的 `providers` 和 `api_keys`。

**理由：** 保持多用户权限隔离，同时允许站点统一决定能够使用的平台种类。

**影响：** 关闭某种类型时保留用户原有配置，停止新任务向该类型发送；重新开放后待处理任务可继续执行。管理员接口不应返回他人的个人平台凭据。

**实现：** `src/catalog.rs`、`src/api.rs`、`web/app.js`。

## D-06 以内置静态页面提供管理界面

**方案：** Rust 直接提供 `web/index.html`、`web/app.js` 与 `web/styles.css`。管理界面默认简体中文，支持手机、平板和电脑。

**理由：** 部署时可以只运行主程序，不需要独立的前端服务。

**影响：** 改动页面后需要重新编译 Rust；界面回归测试和响应式截图检查应随代码提交一起运行。

**实现：** `src/main.rs`、`web/`、`web/tests/`。

## D-07 保留兼容发送入口

**方案：** 除标准 `/v1/send` 外，还兼容 Server酱、PushPlus、Gotify、ntfy 和 Bark 的常见调用方式；所有接口最终使用同一后台队列。

**理由：** 便于现有监控工具和服务器脚本迁移。

**影响：** 调整路由、身份验证和消息参数时需要同时测试兼容接口，并保证接口响应明确表示消息已进入队列。

**实现：** `src/compat.rs`、`src/api.rs`、[API 接入指南](integration.md)。

## D-08 使用数据库迁移与持续构建发布

**方案：** SQLx 在启动时执行 `migrations/`；GitHub Actions 在 `main` 上构建 `edge` Release，`v*` 标签创建版本发布；另有 Docker 工作流构建两种 Linux 架构。

**理由：** 降低新部署时的数据库初始化工作量，并让维护人员有可下载的二进制文件和镜像。

**影响：** 发布之前必须验证迁移和旧版本兼容性；应用回退不会自动撤销数据库迁移。源码中的文档需要与构建版本共同交付。

**实现：** `src/main.rs`、`.github/workflows/`、[运维操作手册](operations.md)。

## D-09 以文件形式维护项目交接资料

**方案：** 在 `docs/` 维护使用、架构、开发、操作、安全、维护台账和设计决定；仓库通过 `scripts/check-docs.mjs` 检查内部链接。

**理由：** 新成员可以从仓库直接了解当前实现、职责和操作方法，文档在代码审查与发布中同步维护。

**影响：** 变更 API、数据库、权限、环境变量、CI 或部署时，应更新相关文档并执行文档检查。

**实现：** [交接入口](handover.md)、[维护台账](maintenance-ledger.md)、[开发指南](development.md)。
