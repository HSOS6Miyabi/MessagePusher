# PostgreSQL 消息队列与后台发送机制

MessagePusher 使用 PostgreSQL 保存消息和待发送任务，并使用 `LISTEN/NOTIFY` 唤醒 Rust 后台工作进程。消息的持久化与任务状态由 PostgreSQL 提供，唤醒通知只负责提醒工作进程及时读取新任务。

## 1. 为什么需要后台消息队列

调用方可能运行在函数计算平台，HTTP 请求有较短的执行时限。一个消息还可能需要同时发送到 Telegram、SMTP 和企业微信；如果逐一等待平台返回，就可能导致调用方超时。

MessagePusher 的标准接口 `POST /v1/send` 在消息成功写入 PostgreSQL 后返回 HTTP 202。后台工作进程随后异步发送，应用可以通过消息 ID 查询结果。

## 2. 数据库中的任务

主要数据库表包括：

| 表 | 用途 |
| --- | --- |
| `events` | 保存一条消息的标题、正文、附件和幂等键 |
| `deliveries` | 为消息中的每个目标 Provider 保存一个发送任务 |
| `providers` | 保存用户配置的渠道和加密后的平台凭据 |
| `provider_catalog` | 保存站点管理员开放的 Provider 类型 |

一条消息发送到三个渠道时，`events` 中保存一条消息，`deliveries` 中会创建三个独立的发送任务。

## 3. 新消息如何唤醒后台工作进程

调用方提交消息后，主程序在一次数据库事务中：

1. 创建消息记录。
2. 为每个目标渠道创建发送任务。
3. 执行 `NOTIFY messagepusher_delivery`。
4. 提交事务。

PostgreSQL 在事务成功提交后通知已经订阅该频道的后台工作进程。后台进程使用 SQLx 的 `PgListener` 等待通知。

**没有新任务时，工作进程会挂起等待数据库通知或下一个需要处理的时间。** 它不再每隔数百毫秒查询一次数据库。

## 4. 多工作进程如何分配任务

每个主程序实例都可以运行一个后台工作进程。收到通知后，工作进程通过以下 PostgreSQL 机制领取任务：

```sql
SELECT d.id
FROM deliveries d
JOIN providers p ON p.id = d.provider_id
JOIN provider_catalog c ON c.kind = p.kind
WHERE p.enabled = TRUE
  AND c.enabled = TRUE
  AND (
    (d.status = 'pending' AND d.next_attempt_at <= now())
    OR (d.status = 'working' AND d.lease_until < now())
  )
ORDER BY d.created_at
LIMIT 16
FOR UPDATE OF d SKIP LOCKED;
```

实际执行时使用带 `UPDATE ... RETURNING` 的查询，领取任务后将状态修改为 `working`，同时记录尝试次数及任务租约到期时间。

`FOR UPDATE SKIP LOCKED` 可以避免多个工作进程同时领取同一行。每批最多领取 16 个任务，各任务使用异步方式发送。

同一个消息下的多个直接发送渠道可以并行处理。共享相同代理地址和密钥的渠道可以组合为一次代理请求，代理再并行调用对应平台。

## 5. 失败重试和任务租约

每个任务最多尝试五次。外部 Provider 返回错误或网络发送失败时，工作进程记录错误原因，并设置下次尝试时间。

默认重试等待时间随尝试次数增加，例如第一次失败后约 40 秒、第二次失败后约 80 秒。达到最大次数后，任务状态变为 `failed`。

正在发送的任务设置了 75 秒租约。工作进程重启或意外退出后，其他工作进程可以在租约过期后重新领取未完成的任务。

如果外部 Provider 已经收到请求，但进程在写入 `sent` 状态之前退出，之后的重试可能产生重复消息。需要避免业务事件重复创建时，请使用 `Idempotency-Key`；需要严格避免外部平台重复显示时，还应在业务层处理事件编号。

## 6. 定时重试与恢复检查

当没有立即需要处理的任务时，工作进程查询数据库中最近的 `next_attempt_at` 或 `lease_until`，并等待至该时间。

由于 PostgreSQL 的通知属于即时信号，数据库连接中断期间可能错过通知。因此工作进程还会执行低频恢复检查，最长等待间隔为 60 秒。这项检查用于连接恢复和异常情况，不承担正常的新消息调度。

`PgListener` 支持连接恢复。工作进程启动时会先注册数据库通知，再检查尚未处理的任务，避免启动期间遗漏消息。

当用户重新启用自己的渠道，或管理员重新开放某种 Provider 类型时，主程序也会发送数据库通知，让等待中的任务及时继续处理。

## 7. 数据库索引与性能

系统为待发送任务的 `next_attempt_at` 以及正在发送任务的 `lease_until` 建立相应索引，便于查询最近需要处理的任务。

这种设计适用于需要可靠存储、并发发送和失败恢复的中小型通知服务。实际吞吐能力仍受数据库配置、网络延迟、任务附件大小、外部平台限额及工作进程数量影响。

数据库中的任务和附件应定期备份，并根据业务需要制定历史消息保留方案。

## 8. 查看发送状态

每个任务的状态包括：

| 状态 | 说明 |
| --- | --- |
| `pending` | 等待发送或等待重试 |
| `working` | 已领取，正在调用外部平台 |
| `sent` | 外部平台接口确认接受 |
| `failed` | 已用尽重试次数 |

可以通过管理页面查看，也可以使用管理令牌查询 `GET /v1/events/{id}`。

## 9. 对外接口与数据库队列的关系

调用方只需在 HTTP API 返回 202 后记录消息 ID。发送密钥用于提交任务，管理令牌用于查询自己账户的发送状态。

如果调用方需要等待多个平台均完成发送，可自行查询对应消息状态。MessagePusher 当前不提供向调用方主动发送完成回调的功能。

更多调用示例见 [API 接入指南](integration.md)。
