## 3. 持续维护项目

此表用于安排后续开发与部署维护工作。状态描述的是当前仓库已有的功能和需要持续关注的事项，不包含未经授权的生产环境配置。

| 编号 | 事项 | 当前情况 | 建议的维护工作 | 负责角色 |
| --- | --- | --- | --- | --- |
| M-01 | 数据保留和存储容量 | 消息、附件没有自动到期清理 | 根据业务规定制定保留期限，实现并测试数据清理，监测 PostgreSQL 容量 | 后端、运维 |
| M-02 | 服务健康检查 | `/healthz` 只表示 HTTP 进程能够响应 | 增加数据库连接、任务积压与发送成功率监测 | 后端、运维 |
| M-03 | 外部平台重复通知 | 进程退出后可能重试已经被外部平台接受的消息 | 根据应用场景定义事件编号和去重策略 | 后端、接入方 |
| M-04 | 代理出站访问控制 | 用户可以配置代理 HTTPS 地址，代码未限制目标主机列表 | 按使用场景配置网络限制并评估应用层地址检查 | 安全、后端、运维 |
| M-05 | 备份和恢复安排 | 仓库提供手动备份与恢复步骤 | 在部署环境配置自动备份、验证恢复、记录恢复目标 | 运维 |
| M-06 | 依赖版本与持续维护 | Rust 依赖清单位于 `Cargo.toml`；仓库当前未提交 `Cargo.lock` | 评估可重复编译要求，定期检查依赖安全更新并验证构建 | 后端 |
| M-07 | 测试渠道安全 | 真实 Telegram、SMTP 测试涉及第三方平台 | 继续使用隔离环境和专用测试账户，限制接收者范围 | 测试、运维 |
| M-08 | 多语言需求 | 目前采用简体中文界面 | 如需其他语言，先规划界面文本与文档的语言管理方式 | 产品、前端 |

具体优先级、负责人和完成日期应由接手团队根据部署风险、用户规模和业务要求确定。实际执行后更新本表状态，并附上对应的代码提交或内部维护记录。

## 4. 发布和交接记录的维护格式

每次发布或重要配置变更后，增加一行记录：

| 日期 | 版本或提交 | 变更范围 | 测试情况 | 数据库迁移 | 操作与文档 |
| --- | --- | --- | --- | --- | --- |
| 2026-11-19 | 以当前 `main` 提交为准 | 整理系统结构、开发步骤、操作、安全和设计决定等交接资料 | 通过 GitHub Actions 检查本次提交 | 现有迁移 `0001`–`0005` | 见 [交接入口](handover.md) |

后续记录应写出具体提交 SHA、测试运行链接及是否需要备份、调整环境变量或数据库迁移。避免在本表复制访问令牌、真实用户数据或运行日志。

## 5. 文档更新约定

- 功能实现或行为变化后，先更新对应使用与开发文档，再提交代码。
- 新增数据库字段或 Provider 类型时更新 [系统结构](architecture.md) 和本台账。
- 重要方案变更后更新 [设计决定](decisions.md)，说明选择原因和运行影响。
- 发布前确认 [操作手册](operations.md) 的命令与当前 `compose.yaml`、GitHub Actions 一致。
- 执行 `node scripts/check-docs.mjs`，并检查 GitHub Actions 中的文档测试。
